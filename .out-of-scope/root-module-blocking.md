# root 模块形态的「完整屏蔽」

本项目不提供 root 模块那种「把系统组件遮起来、把域名全挡掉」的完整屏蔽，也不发布任何需要 Magisk / KernelSU 的产物。

## 为什么超出范围

本工具的形态是「连上电脑或手机版 App，一次性 ADB 执行完就走」：动作只有三类——打开系统设置页拨开关、关闭通知渠道、`pm suspend` 挂起已安装的包；约束是不 root、不常驻、每个动作都能读回、都能还原。

以 #1483 引用的 `FAQQAQ/Kill-Mi` 为例，它做的四件事没有一件落在这三类动作里：

- 目录遮蔽：把 GuardProvider、SystemHelper、MiTrustService 等系统组件连同 `/data/app` 里的更新副本一起遮掉，需要 root 的文件系统挂载；
- 在手机管家里禁用 XSOF / 反诈组件，同样要模块权限；
- hosts 屏蔽 21 个精确域名，要替换系统 hosts；
- UID 防火墙兜底：组件重新出现时按 UID 拦截 IPv4 / IPv6 出站。

这些都需要 root，也就都不满足「一次性 ADB、随时可还原」。要支持它，产品形态本身就得换——常驻模块 + 更高权限，那是另一种产品，不是本仓库的开关审计。

**它自己的代价也和「不影响云服务」相冲突。** 该项目 README 明确写着：地震预警、地震监测志愿者、报警快速定位等功能可能不可用，反诈功能会受影响，ADB 安装验证、运营商设备注册、云查杀及部分云端规则更新也可能受影响；遮蔽 `/data/app` 更新副本后系统还可能清理对应应用的更新与私有数据。换句话说，按引用的那份实现照做，恰恰会动到用户说的那些云服务。

## 与本目录其它几条的边界

- [dhizuku-device-owner.md](dhizuku-device-owner.md)：换权限模型（更高权限的执行后端），本条是换屏蔽手段（直接动文件系统与网络）；
- [miui-telemetry-toggles.md](miui-telemetry-toggles.md)：遥测 / 安全上报一类**开关**不做，判据是「关掉后不产生少广告的效果」；
- [app-install-restriction.md](app-install-restriction.md)：设备策略类（禁装、密码、device owner）不做。

三条各自管一个面，本条不重复它们的理由。

## 不用 root 已经能做的部分

- **挂起广告组件**：`run.py -s <序列号> suspend <包名>` 走 `pm suspend`，并尝试 `cmd connectivity set-package-networking-enabled false` 断网，回读包规则与防火墙状态；`unsuspend` 一条命令还原。断网规则在重启后复位（回到允许），挂起保留——这一点在 [小米清单](../docs/清单/小米-HyperOS.md) 的海外版一节有实测记录。
- **个性化推荐与营销渠道**：按各品牌清单逐项处理，这是「少收到推送」的主要来源。
- **网络层（DNS / hosts）拦截不在范围**：小米清单里记了「网络拦截不在本项目范围，仅作记录」（[小米清单](../docs/清单/小米-HyperOS.md) 的「没有小米账号时 adb 能做的有限」一节）。

用户觉得「还有广告」，通常落在上面第二条覆盖的地方，或落在某个具体页面入口没走通——后者按机型适配处理，把当时的屏贴出来即可。

## 什么时候可以重新评估

如果产品路线改成常驻 App + root / device owner（那时它就不再是「跑一次就还原」的工具），或者 Android 开放了不依赖 root 就能遮蔽组件、按域名拦截的路径，这条才有位置。
