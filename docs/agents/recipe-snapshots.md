# 机型脚本的调用序列快照

47 份专用脚本（43 份 `<型号>.toml` + 4 份按系统版本选的变体）的对外行为，靠一份入库的调用序列快照守着。
数据文件在 [tests/snapshots/recipe_calls/](../../tests/snapshots/recipe_calls/)，一份脚本一份 JSON。

## 快照里是什么

「同一份合成手机、同一组读屏观察下，脚本发出的调用逐条相同」是唯一的判据（spec #1237 的 S1 主 seam）。
每份快照记两个场景，一次调用一行：

```json
["系统广告", "d.shell", ["am start -f 0x10008000 -a android.settings.SETTINGS"], {}]
```

四个字段依次是**段名、方法名、位置参数、关键字参数**。方法名取 `Phone` 门面上的公开方法与
`p.d.shell` —— 有几份助手整段只有一条 shell 命令，只记门面的话它们等于没记。段名是这条调用
发出时正在跑的段（数据里的一个 `[[segment]]`），所以「哪一段变了」能直接从报错里读出来。

- `present`：入口、拉起、落点与读屏观察一律算「在」，脚本沿主路径走到底；
- `absent`：同一批观察一律算「不在」，脚本退到备用分支（菜单、翻页、重试那几圈循环）。

两个场景都记，备用分支才不是空的。合成手机与观察都在
[tests/compare_recipe_calls.py](../../tests/compare_recipe_calls.py)，回归里由
[tests/test_recipe_call_snapshots.py](../../tests/test_recipe_call_snapshots.py) 对当前树代跑：
不建基线 worktree、不联网、不起子进程。

## 什么时候能动快照

**只有行为确实该变的 PR 才能动快照**，而且该 PR 的正文必须写清三件事：哪几份脚本、哪几段、
为什么变。三者缺一，评审看到的就只是「一份 JSON 被重写了」。

这条规则要防的是快照变成让 CI 变绿的橡皮章：比对失败时最省事的动作是 `--write`，而它一句话
也不解释行为为什么变。评审要挡住的就是这种 PR。反过来，纯重构（搬家、改名、抽模块）的验收
恰恰是快照**零差异** —— 所以重构 PR 里出现快照改动，就是它自己承认改了行为。

- 局部搬动、共享段体收进库、词汇上移：零差异，不写快照。
- 真实的行为修正、新增开关、入口或等待策略变化：写快照，并在正文里点名脚本与段。
- 机型脚本新增或删除：快照文件跟着增删（一份脚本一份文件），这是「清单一致」那条守卫要求的。
- 重命名脚本或目录：文件名由路径算出来（`<目录名>__<脚本名>.json`），改名即换文件。

## 怎么动

```bash
python tests/compare_recipe_calls.py            # 比对当前树与入库快照（回归走这条）
python tests/compare_recipe_calls.py --write    # 重写入库快照
```

比对失败的输出先给「哪一份脚本、哪个场景、哪一段」，再给第几条起不同和两边的上下文，照它定位
到具体段体即可。`--write` 与比对共用同一套空转守卫：每份脚本的每个场景都要记到调用，总量低于
`MIN_CALLS` 就算没测到 —— 记录坏掉时 `--write` 拒绝落盘，不把一轮空记录固化成基线。它还会删掉
不再有脚本对应的旧快照文件。

纯重构要「改前改后」两侧证据时，对拍模式仍在（驱动自己拉临时 worktree、跑完删掉）：

```bash
git fetch origin main
python tests/compare_recipe_calls.py --baseline <git merge-base HEAD origin/main>
```

差异为零只能说明「两边做了同一串调用」，不能说明那串调用本身是对的 —— 覆盖面的缺口见下一节。

## 快照看不到什么

- 空页面上走不到的深支：要点名开关的助手（`require_switches` 之后那一段）、只认特定控件的助手
  （单选按钮之类）。它们的正确性由各自的用例守。
- 读屏结果的内容本身：比的是脚本发出的调用，不是它最终关掉了几个开关。
- 段体与库实现之间的名字解析（哪一段需要哪个注入名字）：#1241 的装载期契约用例负责那一段。
- 真机行为：这台合成手机上认不出的页面，真机上发生的事不在快照里。

说清这些是为了不把「快照绿了」当成「行为对」。迁移前的快照可以作为「行为未变」的证据被引用
（spec #1237 的验收清单就是这么用它），但它证明的是调用序列没变。

## 平台

逐条比对只在 POSIX 上跑。同一份假页面、同一份代码，Windows 上会多出 1–2 轮「聚焦 / 锁屏」探针：
还有一处等待循环用着定义时绑死的真实时钟，慢机器上多转一圈（#1239 铺这一层时只在本机 macOS +
3.13 跑过，Windows 侧从未跑通）。本机实测 macOS 的 3.12 与 3.13、以及把假钟调慢一倍，调用条数
都一样，所以这不是解释器差异。把那一处也接上假钟之前，`ComparisonTests` 在 Windows 上跳过；
空转守卫与段名归属那几条照跑。
