# Code review

审查由别的 agent 跑，实现 agent 不给自己打分。这份文件只管「怎么派、什么时候算完」；判断标准在 [CODING_STANDARDS.md](../../CODING_STANDARDS.md)。

## 基线钉 SHA

派审查前先取本分支的基点：`git merge-base HEAD origin/main`，把那个 SHA 和 `git diff <sha>` 一起写进 prompt。不要传分支名 `main`，也不要用 `origin/main` 当时的位置：别的会话合了 PR 之后，那个位置会把别人的提交算进本分支的改动面，各轴会数到不同的树。基点按本地的 `origin/main` 算，取到的比预期旧就先 `git fetch origin main`；分支 rebase、或者把 `origin/main` 合并进来之后，基点会前移，也要重取。

实现若在 `git worktree` 里做，prompt 必须写 `git -C <worktree 绝对路径> diff <sha>`，并把未跟踪的新文件单独列出；同时声明「只审该目录，不看主副本」。不写路径时审查代理在 cwd（通常是主副本）上跑，会审到别的会话未提交的改动与已合并的历史提交。

分工：Spec 轴只核票面覆盖，不查计数；数字对不上归 Standards 轴一次说清。代理报回来的计数自己复核后再写进文档。

## 评审期间冻结工作区

代理跑起来之后不要再改被审的文件。并发上限是 3，五路要分两批，中途改动会让后一批看到另一棵树：候选 1 那一轮三个代理读到同一个文件的三个快照，其中一路把「567 项 1 红」当结论报上来——那条用例刚写完就已经修了，另一路把 ADR 里改前的基线行号当成新文件的行号报错。

要改就等全部回来；等不及就先提交一版再派，让代理看稳定的树。prompt 里要求每路在报告开头注明读到的快照时间。

## 轴的分工

默认三轴：

- **规范**：`CLAUDE.md` 与 `CODING_STANDARDS.md`，只报文档明确点名的条目。
- **bug 扫描**：只看 diff 本身，找会导致功能错误的改动。
- **历史意图**：用 `git log -L` / `git blame` 看被改区域的历史提交，判断是否破坏当年保护的行为。

历史包袱重的区域再加「既往 PR / issue 评论」轴。注释一致性并进 bug 轴一次问完：单开一路的产出通常只有低置信度的措辞问题。

每路 prompt 都写明：只读、不写代码、不往 GitHub 发评论；只回问题清单（文件:行号、一句话、出错场景、0–100 置信度）。

## 结论去哪

- **有 PR**：按仓库格式回 PR 评论，只报 80 分以上的问题。
- **没有 PR**：结论回在对话里，不要为了评论先去建 PR。

代理报回来的问题自己复核再改。改完做一次「撤掉就返红」的验证，别只信代理给的置信度。

## 规模与配额

20 个文件以内的改动用三轴；再多，或者碰到核心状态机（`tool/adb_link.py` 的断线判定、`fast.Phone`、`gui/app.py` 的 `_work()`），才加轴。五路并行受并发上限 3 约束，必然分两批，后一批会读到更晚的树——这也是要冻结工作区的原因。

每路 prompt 圈定 hunk 范围（`git diff <sha> -- <files>`），比「读整个仓库找相关代码」省一半 token。候选 1 那轮五路合计约 70 万 token，其中两路只产出低置信度的措辞问题。

三轴不要为了确认而各自重跑全量回归与对拍：实现刚跑过，重跑只是重复。要跑就跑你怀疑的那一条；其余以实现的运行结果为起点，自己复核差异。
