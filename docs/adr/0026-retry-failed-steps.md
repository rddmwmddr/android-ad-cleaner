# 结果页重试：按步骤 kind 合并，广告开关步按失败段名重跑

基线 `08ae975`。来自 #638：用户跑完一整轮，结果页只给各步的结局与一句话摘要，没有任何重试入口；
要再试一次只能从头跑整套流程。多数没做成的原因是设备侧的（读屏被占用、断线、锁屏、某个 App 的页面换了），
重跑一遍通常就好了，但「从头跑」会连已经成功的步骤一起再做一遍——快照尤其不能重做。

引擎侧原本就能只跑指定段（`fast.py run <脚本> <段名…>` 的 `ONLY`），只是客户端拿不到「哪几段没做成」：
`未完成步骤：甲、乙` 是一行人话，而且段内 `p.setting()` 返 `False` 就 return 的静默跳过连这行都没有（#776）。

## Decision

**一次执行的结果就是这一次的真相；重试另起一次执行，结果按步骤身份合并。**

- **`Task` 加 `kind`**（`backup / recipe / channels / quickapp / ads / finish`）。合并与重试都按它对齐，
  不认标题：`关闭各 App 里的广告开关（3 / 9 段）` 的括号部分两轮之间会变。kind 也写进结果行。
- **可重试 = `rc ≠ 0` 且不是用户停止的那一步。** 这一条同时覆盖三类没做成：失败、读屏被占用 / 断线 /
  锁屏时被跳过的步（`_work()` 给它们记 `rc=3` + `skipped`）、子进程起不来（`rc=-1`）。
  排除的也落在同一个判据里：#577 那三档跳过（没勾 / 这台机本来没有或已做 / 通知没扫成）都是 `rc=0`，
  用户点「停止」的步带 `stopped`。第三档不被重试还有一层原因：扫描是在选择页上失败的，重试这一步时的
  渠道清单本来就是空的，要重扫只能回选择页。**不按 `tail` 里的中文认原因**（ADR-0004 的口径）。
- **合并发生在 `Job.add_result()`**：重试轮的 `Job.results` 从上一轮接管，同 kind 的那一行就地覆盖，
  其余原样留着；标题取上一轮的（`（3 / 9 段）` 说的是用户勾了哪几段，重试轮只跑其中一两段）。
  于是 `snapshot()` / `poll()` / `diagnostics()` / `report_payload()` 拿到的天然就是「各步最新一轮」，
  四处都不用各自再合并一次。已停止的步不在可重试集合里，因此不会被改写成成功或失败。
  `Job.lines` 与 `Job.payloads` 同样从上一轮接管：诊断与上报看的是整场，不是最后那一轮。
- **停止之后照跑的「收尾」不算「被停的步」**：它在结果里没有 `stopped`，若自己失败就是真的没做成，
  会出现在可重试清单里（重试只会再跑这一步）。这是 `runs_after_stop()` 本来的语义，不另开特例。
- **计划由 `retry_plan(当前 Job.plan, 当前 Job.results)` 重建**：广告开关步取该步结果里的 `failed_steps`
  段名（引擎在脚本收尾时随 `未完成步骤：…` 一起发的事件，ADR-0004 的增补段）；脚本中途退出、没留下段名时
  整段重跑。快照只在它自己失败时才重做——重存会把已经关掉的状态当成原状，还原就还原不回去。
  收尾同理：成功过就不再跑（`plan_tasks()` 新增 `finish` 键，缺省仍收尾）。
- **一项都不剩时 `retry_plan()` 返回 `None`，`Api.retry()` 回一句错误**，不起空的一轮：起一轮没有任务的
  执行会把 `Job` 换掉，结果页就被清空了。连点两次也只生效一次，`Dispatcher.start()` 在锁里回绝。
- **两个宿主读同一份判断**：`retry` 的步数由 `Job.snapshot()` 算好放进 `poll()` 的返回值，
  桌面 `showDone()` 与手机版 `RunProgress.parse()` 都只是照着画按钮、按一下调 `Api.retry()`。
  手机版因此不需要在 `aac_android/view.py` 里再写一份——票面原本写的是「判断放 view.py」，
  但两处消费的是同一个 `Api.poll()`，共享一份实现比各写一份更能保证「两处产出相同结论」。
  Kotlin 只加按钮与一次 `retry()` 调用（ADR-0018 / ADR-0019）。

## Considered Options

- **事件带载荷**（采纳）vs **复用 `#aac:payload` 通道**。载荷通道（ADR-0009）进上报日志、给人和脚本看，
  不进界面；这里的段名是客户端做决定用的，语义正好相反。JSON 里多一个 `steps` 字段不改任何既有事件的字节。
- **给事件通道加一个带载荷的 kind**（采纳）vs **ADR-0009「复用事件通道、新增 kind」那条否决**。
  那条否决针对的是把**页面骨架**塞进事件通道：骨架必须进上报，而事件通道的定义就是不进上报，两者冲突。
  这里的段名恰好相反——它必须**不**进上报（是客户端的内部分解），正是事件通道的语义。ADR-0009 记的是
  「骨架这一类数据不该走事件」，不是「事件永远不带字段」。
- **按 kind 合并**（采纳）vs **前端按标题合并**。标题带「（3 / 9 段）」，两轮之间不稳定；两个前端各写一份
  合并逻辑也更容易走岔。
- **合并写在 `Job.add_result()`**（采纳）vs **`poll()` 读时合并**。读时合并要让 `poll()`、`diagnostics()`、
  `report_payload()` 三处都记得调用，漏一处用户看到的就是半份结果。
- **用户手动重试**（采纳）vs **失败自动重试**。自动重试与暂停 / 停止语义纠缠（用户在等解锁、在读日志时
  引擎自己又点起来），而多数失败要机主先做点什么（解锁、重插线）才有意义。
- **不限次数**（采纳）vs **只给一次机会**。判据是「还剩几项可重试」，每轮重算；没剩就不显示按钮。
- **重试轮不重跑已成功的快照**（采纳）vs **每轮都存快照**。后者会把第一轮改完的状态当成「改动前」，
  「还原改动」就还原不到真正的原状了。

## Consequences

- `tool/events.py` 的 `emit()` 接关键字载荷，`KINDS` 多一个 `failed_steps`，并新增 `parse_data()`；
  `parse()` 改为它的薄封装，行为不变。`tool/fast.py` 的 run 分支在打印 `未完成步骤：…` 的同时发这条事件。
  直接跑脚本（没设 `AAC_EVENTS`）的人看到的输出逐字不变。
- `Job` 多两个字段：`plan`（这一轮跑的计划）与 `failed_steps`（本步骤里引擎报的段名，每步开始时清空），
  另加三个可注入的起点（`base_results` / `base_lines` / `base_payloads`，见 ADR-0010 的增补段）。
  结果行每行都多一个 `kind`；真正跑过的行还多一个 `failed_steps`，跳过与停止的行只有 `kind`
  （消费者要用 `r.get("failed_steps") or []` 这种取法）。`tests/compare_api.py` 的对拍输出会因此多这两个键，属预期。（2026-11-13 修订：该驱动已退役，见 [ADR-0011](0011-api-splitting.md) 的增补段。）
- `Dispatcher.start()` 多三个 `base_*` 参数与 `plan_tasks()` 的 `finish` 键；不传时行为与改动前一致。
- `Api.retry()` 是新入口，手机版经 `main.call()` 的通用 `getattr` 直接可调，不需要在 `EXPORTS` 里登记。
- 重试状态只活在当前会话的结果页里：换手机、回检测页或重启 App 之后不再提供上一轮的重试入口（`Job` 换了）。
- 没做真机验证，也没有 Kotlin 编译环境：引擎事件链路在单测里跑通（假子进程的输出 → `_log` → `retry_plan`），
  Android 的按钮与 `retry()` **未编译、未真机验**。
- #776 已落地，但只覆盖**没有兜底**的调用点：这些地方 `p.setting()` 没搜到时改抛异常，本段写进
  `FAILED_STEPS`，因此也被段级重试覆盖。带菜单兜底的几处（如 `honor-PNM-AN10` 的「广告跟踪」、
  `vivo-V2303A` 的「全局搜索」）仍只消费返回值，兜底也不通时照旧不进名单、只能整段重跑。
  改动只在脚本侧，引擎的 `Phone.setting()` 契约没动。

## 增补：补齐有兜底的调用点（#819）

上面那条「只覆盖没有兜底的调用点」在 #819 之后不再成立：`honor-PNM-AN10` 的「广告跟踪」、
`redmi-25060RK16C` 的「系统广告」在菜单兜底也不通时、`vivo-V2303A` 的「全局搜索」在设置搜索
失败时同样 `raise`，本段写进 `FAILED_STEPS`，因此也被段级重试覆盖；搜索成功或兜底走通时行为
与改动前一致。

`tests/test_recipe_setting_checked.py` 的 AST 守卫不收紧：它只看返回值有没有落进判断结构，
`if not` 分支里写 `raise` 还是 `return` 静态分不出；收紧要对分支体做形状判定，而别的兜底靠
带 raise 的 helper（`row()` / `close_named()`）收尾，静态同样看不出来。守住这三处的是行为用例
（redmi / honor 在 `FallbackFailingTooFailsTheSegment`，vivo 在 `test_vivo_v2303a_recipe.py`），
不是 AST。

`vivo-V2303A` 的 `raise` 必须放在「单页跳过」的 `try` 之外：放在里面会被那个 `except Exception`
吞掉，段内结局照样是「成功」。副作用是 `p.setting()` 自己抛的异常（如断线）不再被当成「该页跳过」，
会记成整段失败；`maybe()` / `off()` 抛异常时只跳过该页的行为不变。
