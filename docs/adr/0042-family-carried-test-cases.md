# 测试用例由「族」承载：让删除成为可判定动作

基线 `f1e4abf0`（#1403）。父 spec #1393，落地子票 #1394 / #1395 / #1398 / #1399 / #1400 / #1401 / #1402 / #1403。

## 问题

测试用例只进不出。新增一条断言有制度动力，删除一条没有任何合法动作——因为用例的 owner 是「票」：一票一函数，票不会失效，所以没有任何信号能说明某条用例已经过期。计数只涨、看不见哪一条是多余的。

两份调研已经否证了「按覆盖率删」这条路：`tests/` 里 97% 的用例各自守一个真实分支，删了就是丢覆盖。于是现状是：知道该减，却没有一个可以执行的减量动作。本 ADR 只解决其中一半——**让存量用例的归属从「票」换成可失效的东西，删除变成可判定动作**。增量为什么停不下来、怎么让它停下来，是另一个 spec 的事（换充分性判据，mutation 判据），两者不互相替代，也不互相阻塞。

换 owner 的载体是**族 + 结构句柄**：断言形态同类的用例收进一份数据，每条 case 声明它依赖的结构项而不是票号。结构项退场，case 必须跟着退场；只删 case 不删结构，守卫红。本仓已落地四个族：catalog（装载期拒绝，80 条）、vocab（按脚本冻结的读不出词条，44 条）、entries（入口速查表的行，53 条）、channel_policy（渠道规则词元，111 条）。

## Decision

### 族的容器只管三件生命周期事

容器在 `tests/` 下、非 `test_` 前缀，只承担族的三件生命周期校验：case id 集合与快照一致、每条 case 的结构句柄在当前结构里存在、有产出的族其产出与快照一致（另有可选的缺口校验：从结构反推「每个结构项都该有一条 case」）。容器**不含**「怎么跑被测代码」的知识，也不含断言方法的选择——语料（`handles` / `structure` / `produce` / `expected`）由每个族自己提供，容器不知道任何具体族的形状。

四个族各自的 `violations()` 在各自的测试文件里已有断言；`tests/test_family.py` 的 `FamilyRegistryTests` 再加一层聚合：四个族一次全跑一遍 `violations()`，任一族的自检被删或漂移都在这条聚合守卫里显形。规则是 `dev.tests.family-carries-cases`（注册表在 `docs/agents/rules.toml`，正文指针在 `CLAUDE.md`，判断与反例在 `docs/agents/test-anchors.md` 的「族」一节）。

### 结构句柄从 case 的构造内容派生

每条 case 声明的句柄，必须由它自己的构造内容现算，不写手写字符串字面量。手写句柄等于给结构造第二个 owner，与 `catalog/schema.py` 里「`OPS` 是唯一 owner」的既有约束相悖。catalog 族的 `handles()` 从 case 的 `data` 反推 `(kind, …)` / `("required", kind, key)` 之类，`structure()` 从 `OPS` 现算；entries 族从 `entries.ENTRIES` 现算。结构项退场，句柄校验点名依赖它的 case。

拒绝「结构里根本没有的东西」的行（如 `kind = "explode"`、顶层 `surprise`）句柄为空：它们测的就是那个名字不在结构里，给任何句柄都会说成「这条行依赖某个结构项」，与它要断言的事相反。

### case 只能是纯数据

容器的行必须是纯数据字面量：AST 断言只含 str / number / list / dict / bool / None，不得出现 Callable / Lambda / Name。`family.pure_data_violations()` 用 AST 检查每个族模块的模块级赋值（`Family(...)` 构造本身除外），一个族不能把行为经由辅助常量偷渡进来。写不进数据行的 case（需要 Callable、断言形态不同、输入是子进程 / 真进程 / 需要手机）只能新开一个族或独立成 `def test_`——这样「省力」不会诱导把异质断言塞进同一张表。

### 两根判据分工：快照管删除，结构推导管新增

快照（`tests/snapshots/<族名>.json`）管**删除检测**：case 集合与产出规范化存档，删一条或改一条 case 都会在存档 diff 里显形。结构推导管**新增**：`expected()` 从结构现算「应该有 case」的句柄集合（catalog 族按每个 op 的每个必填键反推，entries 族按 `ENTRIES` 的每一行反推），`OPS` / 入口表加一个结构项，立刻要求配套 case。两根判据各管一头，谁都不替代谁：快照抓不住「新增结构项却没 case」，结构推导抓不住「删了一条 case 却没删结构」。

### 快照更新必须附理由

更新快照只有一个入口：`python3 tests/<族模块>.py --update --reason "…"`，`--reason` 非空才写盘，理由进快照的 `reason` 字段。快照更新不能变成橡皮图章。

### 覆盖面与边界

四个族共承载 288 条 case（catalog 80 / vocab 44 / entries 53 / channel_policy 111）。用 `devtools/unittest_summary.py` 的 `suite_size()` 现算，当前 `tests/` 里 `def test_` 形态的用例数为 3404。两个口径：

- `288 / 3404 ≈ 8.5%`——族承载量 ÷ 当前仍在函数形态的用例数。这是「把族承载量放进现有函数计数」的口径，分母里不含已迁进族的 288 条数据行。
- `288 / (3404 + 288) = 288 / 3692 ≈ 7.8%`——族承载量 ÷ 全部用例数。已迁进族的 288 条 case 现在是数据行、不在 `def test_` 计数里，并把它们并回分母才是「占全量」的字面比例。

两种口径都**低于父 spec 写的「约 15%」**。差距来自：spec 的 15% 是「有可程序访问数据源」的用例上限估计，四族实际只收窄到断言形态同类的那一批（缺键、词元、入口行、规则词元）；其余带数据源但断言形态各异（子进程、真进程、需要手机）的用例按形态判据必须留在独立函数里，不能硬并进族。按批次组织的约 296 条回归用例重新按行为域归组是 #1396，不在本批范围。

## Consequences

- **形态改动难逆转**：case 表 + 快照一旦铺开，退回「一票一函数」没有收益——原来那些 `def test_` 的 owner 本就是票号，退回等于把「可删除」重新换成「不可判定」。族承载的是可删除，不是省代码行；一笔已经付过的架构成本不会因为改回去而收回。
- **快照冻结当前行为，包括 bug**：快照里的产出是「此刻实现返回什么」，不是「正确应该返回什么」。catalog 族的 `outputs` 存的是 `SchemaError` 的**原文**——报错措辞里若有错别字或误导，也会被一并冻结；改正要走一次带理由的 `--update --reason`，而不是让守卫自己判对错。这是刻意的代价：快照是删除与漂移的探测器，不是真值来源。
- **句柄增加写用例成本**：每条 case 要声明它依赖的结构项，比「新建一个 `def`」多一步。这一步正是「删除可判定」的来源——没有句柄，删结构项时不知道哪些 case 该跟着退场；反过来这层成本也挡不住打包批量 case（一条 case 行仍是一行数据）。
- **覆盖面局限**：如上，288 / 全部用例 ≈ 7.8%（或对当前函数计数 8.5%），低于 spec 约 15% 的估计。本 spec 改善的是「存量可删」，不改善「增量增长速率」——后者由 mutation spec 负责。
- **增量为什么停不下来是另一个 spec**：换充分性判据（mutation testing）才会让「增量」有终点判断。本 ADR 只把「存量」的归属换了；两件事不互相阻塞，也不互相替代。
