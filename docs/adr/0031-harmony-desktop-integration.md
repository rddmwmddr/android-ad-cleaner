# ADR-0031：鸿蒙能力并入统一桌面客户端

状态：已实现，待正式发行验收。对应 #890，建立在应用内更新 #888 / PR #889 上。

## 决定

Mac / Windows 的同一个窗口同时提供安卓和鸿蒙设备入口。安卓仍用原来的进程调度和 adb；鸿蒙保留来源项目的 HDC / uitest 引擎，用独立工作线程执行。两种手机的规则和状态文件不混用，不把安卓包操作映射到鸿蒙。

`Api.harmony()` 是明确动作白名单的窗口桥，只把参数转给 `harmony_bridge.HarmonyBridge`；由后者按需构造 `HarmonyClient`，鸿蒙状态不落在 `Api` 上。Android 手机宿主不加载鸿蒙清单和工具。设备枚举只读，必须指定连接列表里已授权、API 范围匹配的序列号才能执行，所有设备命令带 `-t`。

去广告、还原、打开开发者选项使用 `Dispatcher.claim/release`，与安卓去广告、安卓还原和应用内安装更新互斥。检测或执行失败时释放占用；前端过期的异步设备结果不得覆盖换机后的界面。

## 原状态与停止

原始状态按设备序列号哈希命名。引擎 `before_change` 在首次物理点击前触发 `before` 事件；宿主须成功落盘才返回。即使随后断线导致无法确认结果，原状态仍保留。重复执行不覆盖最初原状态；还原只有收到回读成功或已经是原状态时才移除该条。

读取到损坏的还原记录时中止执行，不覆盖原文件。旧独立版记录只在新文件不存在时复制；还原完成后的空文件保留，防止下次重新导入旧数据。

停止沿用引擎的 `holding`：点击后到回读之间不打断。关窗确认后发停止信号、等待启动前检测和工作线程全部结束，再销毁窗口；关闭意图保留到退出，不允许迟到的启动请求执行。还原记录先写副本，成功后再移除内存中的条目；保存失败仍保留还原入口。不执行全局 `hdc kill`，以免断开其他工具的连接。日志只写规则名称、结果和错误类别，不写页面原文或设备序列号。

## 事件通道与移植边界

鸿蒙引擎的四种进度事件（`before` / `segment` / `switch` / `retry`）只经 `HarmonyClient` 的回调进入窗口桥，不走 `tool/events.py` 的行格式，也不受 ADR-0004 那六个 kind 的约束；它是并行的第二条事件通道，两边的词表不要互相套用。

`Screen.switch_for` 没有移植上游 `Screen.ets` 的右侧上界（`item.rect.left <= title.rect.left + windowRect.width`）。落在同一行、但在标题右侧一整屏之外的 checkable 节点，也会被认成这一行的开关；这是已知的语义差，改动读屏时先看它。

原创与移植的分界：约 310 行与 `entry/src/main/ets/engine/Screen.ets` / `Phone.ets` 逐条对应（常量与判定流程），改动时要和 `.ets` 对拍；其余约 765 行——`harmony_client` 的设备枚举与持久化、任务编排、`harmony_vocab` 的解析、前端鸿蒙段、打包胶水——没有上游对照物，是本仓库原创，按本仓库标准评审。`Phone.ets` 依赖的 `../hdc/HdcClient` 未入库，无法独立核对。

## 打包与范围

源码解析原 `Recipes.ets`；发行包使用受一致性测试守卫的 `harmony/recipes.json`。HDC 与共享库不入库：`gui/hdc_fetch.py` 在构建期按平台从 OpenHarmony `7.0-Release` 下载、按钉死的 SHA-256 校验并解包；`bundle_data()` 把该平台的一套放进打包资源，并保留原许可声明。Mac 签名覆盖这些二进制文件。源码运行先跑一次 `python gui/hdc_fetch.py`，缓存目录可用 `AAC_HDC_CACHE` 覆盖。

规则来源为 `harmony-ad-cleaner@179520d` 中 HOP-AL10 / 7.0.0.111 的实测记录。迁移通过离线用例不等于对其他机型做过真机复测。统一客户端本次合并没有增删规则词条；不引入整应用通知总开关、系统包卸载或系统更新操作。
