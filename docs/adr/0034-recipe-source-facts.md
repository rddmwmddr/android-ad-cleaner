# 机型脚本的事实由一份纯 AST 层给出

> B 段（catalog）另由 [ADR-0038](0038-recipe-catalog.md) 取代：按 import 归属解析（`surface_sources` / `imported_sources` / `injected_calls` / `step_sources` / `strategy_sources`）随注入面一起消失，事实层退化为代码里的字面量提取器，`scan_source` / `scan_dir` 与字面量投影保留。
>
> 部分由 [ADR-0037](0037-recipe-declarative-loader.md) 取代（2026-11-13 修订：脚本顶部多了 `from recipe_kit import step` 与一份 `if TYPE_CHECKING:` 导入，行号与调用写法保持不变）：事实层仍只读 AST。正文保留当时的决定与取舍。

基线 `2434cb1`。

维护者有两套词法读同一批 43 份机型脚本：入口速查（`tool/entries.py`）按正则切实参、按位置猜赋值；词库（`tool/vocab.py`）走 AST。同一份脚本被解释两次，修一处漏一处——`oneplus-PJA110` 的 `p.start(package, activity=START_ACTIVITIES.get(package))` 就被正则截断过，只因截断后的第二实参既不是字面量也不是标识符、被当时那道严格性检查挡掉，才没有污染生成物（#1156；那道检查是 #1197 删掉的 `_arg_at`）。更紧的是 #1149：段体搬进注入面之后，`p.off(only=[...])` 的字面量会离开脚本，「从脚本现算词条」这条数据源就断了。需要一层能同时回答「这台机用了哪些入口」和「这段关掉了哪些词」。

## Decision

### 模块边界与依赖方向

`tool/recipe_source.py` 是第三份「读机型脚本」的模块，与 `recipe_meta`（头部元数据）、`recipe_kit` / `recipe_nav`（运行时前导与导航）并列。依赖方向是 `entries → recipe_source ← vocab`：事实层不 import 任何消费方，不碰手机、不读屏、不连带 `adbutils`，没有设备也能跑。

扫描入口只有两个：`scan_dir(recipes_dir, families=None)` 给出「相对路径 → 事实」，`scan_source(src, bindings=None)` 给出单份源码的事实；注入面另由 `injected_sources()` 供源码（见下文）。遍历口径（`recipe*.py` 的 glob、相对路径写法、品牌过滤）只在 `scan_dir` 写一次，两个消费方不再各写一份；不做缓存。

### 事实层只出调用点清单，不做分类

每条 `Call` 带归一后的调用名、实参（每个 `Arg` 记录解析出的字符串、原文、所属形参位置）、所在函数、行号与页面标签；`Facts` 另外给出模块级函数名（本地定义会盖住注入版）与模块级字典的常量键值对——后者只为让词库不再自己解析一遍。

分类留在消费方：词条方向（`polarity.want_state()`）与页面到分组的映射在 `vocab`，入口键与直达 / Intent / 搜索的区分在 `entries`。事实层不认词表、不判极性。

「读不出」是一个保留态，靠 `Arg.resolved` 区分：`values` 为空且 `resolved=False` 是读不出，原文进 `Arg.text`；`resolved=True` 而 `values` 为空是解析成功但值本身为空（`only=[]`）。入口侧要包名、词库的「未解析」清单要原文，两者取同一份事实。

### 注入面按源码扫，不写声明式元数据

脚本把导航搬进注入面之后只剩一行调用、入口写在实现里（#1153、#1154）。事实层提供 `injected_sources()`：延迟 import `recipe_nav`，用 `inspect.getsource` 取每个注入名的实现源码，交给同一个 `scan_source`。`g["X"](…)` 与裸名 `X(…)` 归一成同一个调用名并标 `injected`。

不在 `recipe_nav` 的每个簇上声明入口元数据：那会造出第二个真相源，实现改了元数据没改就静默漂，而漂掉的正是「哪些机型用过这个入口」。跨文件的形参回填（实参在脚本里、形参在实现里）也不由事实层回头读调用方，而由调用方按位置传 `bindings={形参位置: (字符串, …)}`，依赖方向不反转。

### 严格复刻旧语义，修正留给以后的票

- 变量的值取「文件内、位置之前最后一次同名赋值」，不分作用域；最后一次赋值读不出时返回空，不退回更早的值——退回会把入口速查记成另一个包。
- 形参回填只在同一份源码内做，且只从函数定义之后的调用处取；注入实现的调用处不在本文件，返回空。

一处刻意偏离：不复刻旧正则对赋值字面量的 `[\w.$]` 字符集卡。那道卡只作用在「按位置猜赋值」这一条路上，同一批串在源码正文里本来就看得见（`hot_news` 整条命令串是被正则直接捞到的）；收成一份事实后只剩一种读法，再卡会把这类机型的出处读丢。实测放开它，两份生成物一字不变。

一处刻意改变：`used_by` 遇到语法错的脚本，从「照着能扫」（旧词法不用解析器）变成抛 `SyntaxError`，不做容错返回——静默少几台机型比崩掉更糟。

### 语义修正的边界

改的是读法，不是结论。`entries` / `vocab` 的生成物格式与公开签名一个不动，`recipe_meta` 的头部解析、脚本的 `p.*` 接口与任何用户可见文案不在范围内。验收判据是两份生成物 `diff` 为空，不是逐行比对两个实现。

## Considered Options

- **在 `recipe_nav` 的每个簇上声明入口元数据，事实层按元数据取**（否）。元数据与实现是两份要同步维护的东西，树里没有任何守卫能让它们一起改；而「按源码扫」在注入实现里本来就读得到同一批调用。
- **事实层自己跨文件去找调用方，补齐注入实现的形参**（否）。那要事实层知道「谁是调用方、脚本目录在哪」，依赖方向反转，且与「读任意源码字符串」的入口形状冲突。调用方按位置传 `bindings` 能拿到同样的结果，还少一条隐式约定。
- **解析不出时跳过该脚本或返回空事实**（否）。这正是这次要消灭的失败模式：入口速查静默少几台机型，谁也不会发现。抛 `SyntaxError` 会把问题立刻暴露在生成命令上。
- **顺手修正赋值作用域、放宽字面量字符集、给认不出的调用加诊断输出**（否）。验收是「逐字不变」，混进语义修正后，两份生成物的每一处差异都得分清是「换实现」还是「改结论」。修正单独开票。
- **保留旧正则那条 `[\w.$]` 卡**（否）。见上「一处刻意偏离」：它只挡一条读法，而丢掉的是 PLZ110 / PMX110 的出处。

## Consequences

- 入口速查与词库不再各有一份脚本解析；`entries.py` 与 `vocab.py` 里已无自己的 `ast.parse` 与实参词法。
- 事实层进 mypy 严格档（逐项 flag，与 `polarity` / `plan` 等纯逻辑模块同一判据）。
- 事实层能读任意源码字符串，也能按注入名取实现源码，所以 #1149 接线时不需要改这一层的接口，也不需要再造一套解析。
- 脚本语法错会让生成命令直接失败，而不是少几台机型。这是刻意的取舍。
- `close_named` 函数体里的 `p.off()` 算不算「未解析」仍留在词库判定，事实层只报「这条调用在哪个函数里、名单是不是形参」。
- 这次没有接上「注入实现里的 `p.off` 也产词」：今天没有任何脚本能验证那个分支正确，#1149 接线时一并验收。
