# 机型脚本的前导由引擎注入

基线 `cd77080`。

40 份机型脚本各自在文件头写一遍「一段怎么开始、怎么结束、失败记在哪」：段包装 `step()`、必需入口断言 `require()`、可选入口助手 `maybe()`、段过滤名单 `ONLY`、失败台账 `FAILED_STEPS`。这些副本已经分化成两代：锁屏时一代抛异常（记为未完成），一代直接返回（不留记录，结果页报「关了 0 个」）。引擎想统一这个行为，改不到已经发出去的那些脚本副本（#838）。本票只做机制、不迁移真实脚本，它是 #839 的前提。

## Decision

**前导由引擎在执行脚本时注入，脚本不再自己定义这些名字。**

- **注入而非 import。** 段包装必须绑定当次的 Phone 与这一次的执行作用域（`ONLY` 名单、两个台账都在里面），import 来的模块级函数两者都拿不到。做成 `from recipe_kit import step` 就得把 Phone 与名单当参数传下去，等于让每份脚本再写一遍绑定代码。注入后脚本拿到的是已经绑好的闭包，写法和以前一样。
- **三个执行点注入同一份**：引擎跑脚本（`fast.execute` 的 run 分支）、适配自检（`adapt.check_draft`）、测试装载（`tests/fixtures.load_recipe`）。漏掉任何一处，就会出现「生成时安全、执行时不安全」——自检通过而真跑不记账。
- **复用 `ScreenLocked` 做中止信号，不新造类。** 它在引擎里的语义已经是「停下整批、不逐项报同一个原因」，且已有机型脚本用它表达同一件事。新造一个中止类会让同一种状态有两个名字，调用方还得判断该接哪个。
- **段过滤名单在段包装被调用时从执行作用域读，不做初始化快照。** 现有测试会在装载之后重绑或清空 `ONLY` 再单独驱动某一段；WKL-AN20 另有在段内读它做自门控的写法。快照会让这两种都看不到新值。
- **失败台账是执行作用域里的同一个列表对象**，引擎收尾与适配自检都按引用读；跳过台账 `SKIPPED_STEPS` 独立，不参与退出码。
- **退出码只保留 0 与 1。** 不新增「中止」专用取值：引擎里已有的 `2` 表示「本步骤一步都没执行」，跑中中止与之矛盾；客户端内部已占用 `3` 表示跳过。失败原因由日志行表达。
- **脚本的本地定义仍然覆盖注入的名字。** 迁移之前跑任何现有脚本，用户看到的东西一个字节都不变；注入只有在新写的（或不带本地前导的）脚本上生效。

## Considered Options

- **做成可 import 的 `recipe_kit` 模块，脚本 `from recipe_kit import step`**（否）。段包装要绑定当次 Phone 与执行作用域，模块级函数拿不到；要让脚本传进去，每份脚本又得写一遍绑定代码，前导就没被收口。
- **用新造的 `Halted` / `Aborted` 异常表示中止**（否）。`ScreenLocked` 已经承担这个语义，两代脚本里也都在用它；再造一个同类只会多一种要辨认的名字。
- **初始化时把 `ONLY` 快照进段包装**（否）。现有测试与 WKL-AN20 的自门控都在装载之后读写名单，快照会让它们看到旧值，而且是那种「跑得通、只是判错段」的静默错误。
- **本票顺带迁移 40 份真实脚本**（否）。迁移会改变用户可见行为（锁屏之后剩余段从「静默跳过」变成「记未完成、退出码 1」），与「机制层行为零变化」的验收冲突；混在一票里，行为回归与机制回归的失败分不开。迁移在 #839。

## Consequences

- `tool/recipe_kit.py` 是引擎侧这份前导的唯一实现；三个执行点各加一行 `preamble(p, g)`。它不是仓库里前导的唯一副本：40 份脚本与 `adapt gen` 生成的草稿（`adapt.py` 的 `DRAFT_HELPERS`）都还自带本地定义，覆盖注入——迁移之前，这份注入只在没有本地前导的脚本上生效（#839）。
- 除了六件，执行作用域里还多两个名字：`HALTED_STEPS`（中止之后没轮到的段，`FAILED_STEPS` 的子集）与 `HALTED`（中止标记）——前者让 `report_run()` 把「因中止未执行：…」另起一行，后者让后面的段包装不再碰手机。它们不改变失败台账：第一行与 `failed_steps` 事件仍是全部段名，与 [ADR-0004](0004-engine-state-events.md) 的「同一份数据」不冲突，结果页的重试会把中止的段一起带回来（[ADR-0026](0026-retry-failed-steps.md)）。
- `SkipStep` 与 `skip()` 都按执行作用域里的当前值取，脚本只换异常类、仍用注入的段包装时也抛接同一个类。
- `CONTEXT.md` 的「未完成步骤」从「抛了异常的那一段」扩成「没跑成或没轮到的那一段」，并新增「跳过台账」词条。
- 本票不改 `docs/04` 的写脚本说明：迁移之前脚本仍要自己写前导，现在改口会让新写的脚本依赖一个还没铺开的行为。等 #839 剥掉 40 份的本地定义后再一起改。

## #839 之后：迁移结果与四个可选钩子

43 份机型脚本的本地前导已全部删除，`docs/04` 改成「前导不用自己写」，`adapt gen` 的草稿也不再带。**当时白名单是空的**：票面预判的可选入口例外（`oneplus-PLR110` 的 `maybe()`）没有出现，改用注入的 `p.entry()` 后它的既有用例照常绿。白名单后来不再为空——#939 之后有两处 `page` 例外，见下一节。

本地副本除了「锁屏怎么办」，还藏着三件不属六件套的东西，直接删会连带删掉有测试守着的行为。它们按同一个形状收进前导——脚本定义、引擎在对应时机调用，不定义就什么都不做：

- **`guard()`**：段入口、读锁屏之前调一次。7 份脚本（`honor-WKL-AN20`、`meizu-MEIZU 21 Pro`、PHK110 与 PHK110-15、PKX110、PKH110、RMX3700）原本在段包装里逐段比对型号 / 版本；现在写成一个 `guard()`，判别式原样保留（`skip(...)` 记跳过，`require(...)` 记未完成）。
- **`wrap`**：段体外面套的上下文管理器。`honor-WKL-AN20` 原来写 `with safe_ui(): action()`，现在 `wrap = safe_ui`，段包装替它进这个 `with`。没有这个钩子就会丢掉 `safe_ui` 对自绘开关的截图屏蔽——引擎后来加的坐标 / 尺寸守卫与它重复，截图屏蔽不重复。
- **`detail()`**：失败那一行之后多打一行现场摘要。`meizu-MEIZU 21 Pro` 原来在段包装的 `except` 里打 `page_summary()`（报 Activity 与计数、不带账号页文字），现在 `detail = page_summary`。
- **`RESULTS`**：脚本定义这个列表时，段包装按 `完成` / `跳过` / `未完成` / `未执行` 记一条。9 份脚本原来的状态词各自一套（`completed` / `skipped` / `version_mismatch` / `locked` / `已回读`），统一成这四个。段体自己 `return False` 表示「这一段没做全」的，仍记 `未完成`——与迁移前一致，只影响这一行分段结果、不进失败台账、不改退出码（要不要让它算失败是另一个判断，本票不动）。段抬头那行也统一成「`== 段名`」：WKL-AN20 原来在这行引它的 `CHANGES` 表说这一段要动什么，现在只有段名（`CHANGES` 表没动，只是 `run.recipe_meta` 列段名本来走的就是源码里的 `@step("…")` 字面量，与这张表无关）。

四个钩子都必须在第一个 `@step` 之前定义：`@step` 是执行式装饰器，段体在装饰那一刻就跑，段包装也是那一刻去作用域里取 `guard` / `wrap` / `detail` / `RESULTS`。

迁移顺带带来的两处行为变化，记在这里，不归「锁屏」那一类：

- **断线不再逐段记账。** 大多数本地副本把 `adb_link.DeviceLost` 当普通异常收进 `FAILED_STEPS` 后继续往下跑；注入的段包装在 #838 就定了「交还引擎、整轮停下」。迁移后全族统一为后者：退出码仍是 1，结果页看到整轮断线，而不是后面必然全灭的一串段名。守着旧行为的两条用例（`test_direct_entries_667`、`test_recipe_fast_entries_796`）改成断言异常上抛，它们原本要守的「断线不许当成入口改名去走菜单」不变。
- **`adapt gen` 的草稿不再带前导。** 草稿由 `adapt check` 自检时同样注入；留着本地副本，新写的脚本会把两代实现的坑重新挖一遍。

守卫分两层，都在 `tests/test_recipe_preamble_migration.py`：结构层用 AST 禁止 43 份脚本再定义那六个名字（并检查 `adapt gen` 的草稿），行为层给每份脚本四个场景——跑前锁屏、首段失败、中途失败、中途锁屏——断言失败台账非空且退出码 1。跑在 `debd435` 的干净副本上，两个锁屏场景各 32 份红：26 份是票面说的那句「后面的都不跑」然后返回，5 份（PHK110 两个变体、PKX110、PKH110、RMX3700）把 lock 记进本地 `RESULTS` 后返回、退出码同样是 0，再加上 `honor-WKL-AN20`（本地段包装拿段名去查自己的 `CHANGES` 表，探针段名查不到、直接 `KeyError`）。`meizu-MEIZU 21 Pro` 迁移前就记了失败台账，是绿的。迁移后 43 份 × 4 场景全绿。

## #902 之后：注入面多一个 `start_or_skip`

注入的名字从六件扩到七个：`start_or_skip(包名, 页面, dead_ends, 原因)`。它包住 `p.start(包名, 页面)`，
在报错是「没有进入前台 / 启动后离开前台」、且报错里带的落点命中 `dead_ends` 时 `skip()` 收尾，
其余照原样上抛。

为什么不放进引擎：落点算不算「入口不可达」是机型的实测结论（小米 / 红米缺主题商店时，
主题管理包的代理页会被系统转去应用商店详情页或桌面），不是 `Phone.start` 该有的判断；
`Phone.start` 的前台断言与报错格式保持不变，段体在异常之后决定这一段的结局，与 ADR 里
「段体区分跳过与失败」的既有分工一致。落点从报错原文里取，不重新读前台：抛出之后再读有一小段
窗口期，前台已经切走会判错。

`tests/test_recipe_preamble_migration.py` 的禁定义名单随之加上这个名字。`tests/test_theme_unreachable_902.py`
守着三种落点与两个反例（别的 App 顶掉、断线），并逐份跑 15 份小米 / 红米主题脚本。

## #903 之后：注入面多一个 `require_switches`

注入的名字从七个扩到八个：`require_switches(读到的开关, 名单, 页面, optional=(), contains=False)`。
它顶替的是原本在 14 处机型脚本里各写一份的「点名开关没全部出现就整段不动」守卫，
失败时的文案与判据不变，只在报错末尾补上读屏基座 `Screen.page_evidence()` 的现场。

为什么不放进引擎：名单是脚本对某台机某页的实测结论（哪几个开关必须一起在），
引擎的 `off()` 只认 `only=` / `keep=` 的子串匹配，本来就不做「缺一项就整段不动」这个决定；
把它搬进 `plan_switches()` 会让引擎替脚本判断一项缺失该不该停，那是 ADR-0008 分工的反向。
页面证据反过来属于引擎——「停在哪个页、页面上有哪些开关」只有读屏基座读得到，
所以 `page_evidence()` 在 `Screen` 上（ADR-0033 之后门面只转发），`require_switches()` 只是把它接进报错。

收成一处要守的是判据等价：小米系的 `contains=True`（标题可能附带整段说明）、
PMX110 / PLZ110 的 `optional`（部分安装版本没有那一行）、honor 的「整页所有开关且空页算失败」
都要原样保留；`tests/test_missing_switch_evidence_903.py` 守着三种输出（缺项 / 空页 / 通过）
与「文案只在 `recipe_kit` 一处」，`tests/test_recipe_preamble_migration.py` 的禁定义名单随之加上这个名字。

## #909 之后：注入面多一个 `skip_in_safe_mode`

整页关闭的段落（逐 App 的广告跟踪列表、应用建议卡片、文件夹底部的更多推荐）在安全模式下
一个开关都点不到：`off()` 只关脚本点名的开关（ADR-0008 的 `plan_switches`）。段落随后回读
「必须全关」就必然记成语义错误的失败——它其实什么都没做（#909 的 PKT110 上报）。这类段落在
安全模式下的唯一结局是「跳过并说明」，出口收成前导的 `skip_in_safe_mode()`，原因文案只在
`recipe_kit.SAFE_MODE_PAGE_WIDE` 一处。

为什么不放进引擎：整页关闭是脚本对某台机某页的实测结论，引擎的 `off()` 只管「这一页拨哪些」，
判断这一段的结局属于段体（本 ADR 开头的分工）。让它从 `off()` 里抛跳过更糟——同一条段里先关的
点名开关已经生效，整段却被记成跳过，结局比失败更不准确；而且调用方无从知道哪一行会中止。

12 处整页关闭的段落各加一句：PKT110、PLP120、PLR110、PHK110、PKX110、PKH110、RMX3700 的广告跟踪，
PKT110 与 RMX3700 的应用建议，honor-PNM-AN10 的广告跟踪 / 桌面文件夹 / 主题。混着点名开关的段落不动——
那些行在安全模式下照常跑，页级说明由 `off()` 的「安全模式不做整页全关」那句给出。

还有一条不走 `p.off()` 的路：vivo 的两份脚本各有一个 `off_unnamed()`，按坐标点商店
「个性化推荐」页上无标题的开关（#220）。它自己读一次点一次、只回读点过的项，不会产生本票的
假失败，但在安全模式下照样会点这些没点名过的行——与 `plan_switches` 的「只关点名的开关」相抵。
两处都改成安全模式下直接返回并打一句说明；这一段里还关着点名开关，不能整段跳过。

`tests/test_safe_mode_page_wide_909.py` 两头都守：行为上逐段跑一遍安全模式与非安全模式，
结构上用 AST 认出「整段只做整页关闭」的段，要求它的第一句就是 `skip_in_safe_mode()`；
判据本身另有一条用例（经助手间接整页关闭也算、混着点名开关的不算）。

## #908 之后：包没装由 `Phone.start` 判，结局是跳过

`Phone.start()` 在启动命令失败、手机确认在线、`pm path` 里没有任何 `package:` 时抛
`recipe_kit.MissingPackage`（`SkipStep` 的子类）：段包装记跳过台账、整轮退出码仍是 0，
跳过原因里带包名。同一判定点的另外两种结局不变——包在但拉不起来仍是 `RuntimeError`
（未完成，报错带系统原文），断线仍是 `DeviceLost`（整轮停下）。0.4.1 的 125 份上报里
27 份带「本机没有安装」，跨小米 / 红米 / OPPO / 一加 / 荣耀 / 真我，不是国际版独有。

为什么不放进脚本：这个判定要把三件事合在一起——启动失败、`Phone.start` 自己的断线判据、
`pm path` 空——只有引擎那一处同时拿得到；18 份脚本已经各自写了一份 `pm path` 早退，再让新脚本
抄一遍只会多一份会分叉的副本。这也是国际版（HyperOS 版本号 `MI` 后缀）ROM 不写专用机型脚本的
理由：它缺的是几个 App，不是另一套界面，缺的段由引擎判、剩下的段用固定参考脚本跑（docs/09）。这一条与「#902 的落点不算入口不可达」不冲突：那里判的是
「App 在、被系统转走」，这里判的是「App 根本不在」，后者不需要任何机型结论。

为什么沿用 `SkipStep` 而不新增第五种结局：这个 App 在这台机上本来就没有，与「按约定不跑」是
同一件事，台账、结果页与退出码的口径都相同；多一个类型只会让每个调用方多判一次。
段包装的接法因此是 `except (g.get("SkipStep", SkipStep), MissingPackage)`——脚本只换跳过异常类时
（ADR 里「抛的和接的仍是同一个类」那条），引擎这一路的跳过也得接住。

脚本侧要一起改的是「先试直达、失败再走菜单」的助手：它们按 `except RuntimeError` 收下
「这条路不通」，跳过若被吞下，这一段会退化成走菜单后的空跑或假失败。判据只认类型
（`except SkipStep: raise` 写在宽捕获之前），不按中文文案判。`start_or_skip()` 的说明同步改成
「没装也上抛，由段包装记跳过」。`tests/test_missing_package_908.py` 守着三种结局、段级台账与
整轮退出码，并逐段跑一份带该助手的参考脚本，确认它不再退到菜单那条路。

## #939 之后：注入面多一个 `page`

「打开设置页并确认落在哪儿」的判据（包名、Activity、页面标题）在 `oppo-PMX110` 与
`oneplus-PLZ110` 各有一份复制品，三段失败都只抛一句错、不留现场：#910 的
「未确认页面「游戏中心」」分不清是标题改名了还是页面根本没加载完，而这正是那一段
（以及半边「资讯服务」开关名）当前唯一的取证手段。

注入面加第十个名字 `page(标题, 包名=None, Activity=None)`：三段失败时先 `p.note_miss()`
打一行与入口失败同形的现场（停在哪个 Activity、结构摘要），再抛原来那句错。报错文案是上报
与用例逐字认的第一句，因此现场走独立输出行、不拼进消息；两份复制品删掉，改为消费注入的这份。
现场行里「没找到」的是这一段缺的那样东西——包名、Activity 或标题，不是一律写标题：
落点跑偏时标题往往就在屏上，写成标题会把人引去查改名，正是这类失败要分开的两种情况。

为什么不把现场拼进报错：`note_miss` 那行是 `Phone` 的既有输出契约（#901 的负一屏入口、
`row()` 的入口失败都靠它），拼进消息会让同一类失败在客户端里出现两种形状。
