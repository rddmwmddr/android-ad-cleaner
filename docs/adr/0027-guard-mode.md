# 守护模式：独立只读复查，按锁屏状态分路，结局分四档

基线 `914cec5`。来自 #623 第 5 项与 #794：手机版对外发测试版前要有「定期只读复查被改回的开关并
发通知」。落到代码上先撞到三件事：`run.py` 的 `check` 并不回读任何开关（只读锁屏、机型脚本版本匹配、
广告包挂起状态），真正只读的只有 `chan_fast.py -s SERIAL verify`，而它只认渠道清单；机型脚本的开关
没有非 UI 的读法，复查要逐页导航；`wait_unlocked()` 只点亮屏幕、**等机主解锁**，不代替解锁。

## Decision

**守护复查是独立于执行的一次只读检查，不点击开关、不改设置。**

- **守护模式是 App 内一个默认关闭的选项**，开启时由用户选范围：只查渠道，或连机型脚本开关一起查。
  默认关是因为没有真实发生率的证据——`docs/`、`recipes/` 与全部 issue 里找不到一条「开关被改回」的
  记录；搜到的「重新打开」都来自还原流程、厂商切服务要重签协议、系统重置。这是防御性设计，不是已证实的
  故障。
- **审计模式让 `off()` 变成只读，机型脚本一个字都不用改**。40 个文件调用 `p.off()`，逐个换成
  `p.audit()` 等于让每一份脚本都跟着动。`fast.py -s SERIAL audit 机型脚本.py` 打开模块级开关，
  `off()` 走同一套 `plan_switches()` 与页面循环，只是不点击开关本体；**导航仍然点击**
  （`start` / `entry` / `setting` / `tap` 照常执行）——不点进去就读不到页面。这是全仓库最热的路径，
  所以默认路径的行为必须由测试钉死。
- **结局分四档，不复用 `readback()`**：`readback()` 把「标题不在列表里」和「明确读到非目标态」都归成
  MISSED，而守护复查必须区分「被改回」与「这一行不在了」。四档是**被改回**（明确读到该行、状态非目标态）、
  **找不到**（页面上没有匹配标题的行：改名 / 换页 / 入口没了）、**灰的**（行在，被上级开关禁用）、
  **未确认**（读屏失败 / 断线 / 中途锁屏）。`readback()` 的 MISSED 语义不能改——它喂着 `off()` 的记账。
- **触发以充电为硬条件**，时机是每周一次 + 系统更新完成后 + App 内手动「现在查一次」。
  **结果与上次相同就不发通知**：一台干净的手机每周报一次「0 项被改回」，用户会直接关掉通知，
  这比不做更糟。
- **按锁屏状态分路**：

  | 手机状态 | 渠道 | 机型脚本开关 |
  |---|---|---|
  | 熄屏、未锁屏、充电 | 自动跑，不亮屏 | 自动跑：亮屏 + 全屏检查页 |
  | 锁屏、充电 | 自动跑，不亮屏 | 不跑，发一条通知提醒 |
  | 亮屏、未锁屏、充电（用户在用） | 自动跑 | 不跑，等下次熄屏 |
  | 不充电 | 不跑 | 不跑 |

  渠道复查是纯 `dumpsys notification`（`chan_fast.py` 的 `ShellPhone`，不启 UiAutomation），
  锁屏下成立；机型脚本复查要导航，锁屏下不成立。**设了 PIN 码的用户熄屏后很快转锁屏**，
  「熄屏且未锁屏」这个窗口对他们几乎不存在，所以机型开关复查实际主要走「通知提醒 → 点开」。
  这条要写进设置页那一行说明，不是设计缺陷而是边界。
- **通知点开先列清单，再动手**：被改回的项按「页面 · 标题」逐条列出（默认全选），用户点「全部关闭」
  才执行。「一键」的语义保住了，但这条链路的起点是自动触发的推断——厂商 OTA 之后我们对「这行还是原来
  那行」没有绝对把握，让人看一眼再动手比省一次点击值钱。
- **通道拿不到时不静默**：Shizuku 未授权、无线调试被关且没有 `WRITE_SECURE_SETTINGS`、配对失效时，
  第一次失败发一条「守护模式需要重新授权」，之后静默；**连续 3 次失败自动关掉守护模式**并在 App 内
  说明原因。静默跳过的失败模式是「用户以为在保护他，其实一次都没跑过」，比不做更糟。
- **首次开启需要一份渠道清单**：没有清单时开关置灰，提示先跑一次完整清理。允许开启并现扫一遍会把
  「从来没关过的几百条广告」报成「被改回几百项」。
- **上次复查结果按型号存一份** `<备份 root>/guard-<型号>.json`（时间戳、四档结局的键、渠道清单的指纹），
  照 `ui_hidden.py` 的做法。「无变化不发通知」「连续 2 次找不到才提示重新适配」「连续 3 次失败自动关」
  三条都要它。不写进备份目录：下一次清理会覆盖（#651 刚为这个踩过坑）。

## Considered Options

- **每周轮询 + 系统更新后**（采纳）vs **只在系统更新后 + 手动**。前者空转率高，但加上「无变化不发通知」
  后成本可控；后者在厂商云控改开关这类无时点的情形下永远不触发。
- **按锁屏状态分路**（采纳）vs **锁屏时也自动跑全量**。`wait_unlocked()` 的语义是「等机主解锁」，
  无人值守时它只能等满预算然后失败。
- **审计模式改 `off()`**（采纳）vs **给 40 份脚本各加一个 `p.audit()`**。后者每次新增机型脚本都要
  记得写两套调用。
- **四档结局**（采纳）vs **复用 `readback()`**。后者把「找不到」当成「没到目标态」，OTA 改名会被报成
  「广告被打开了」——正是这张票最该避免的误报。
- **通知 → 清单 → 一键关**（采纳）vs **点通知直接开跑**。自动触发的推断不应该跳过人的一眼。
- **通道失败发通知 + 连续 3 次自停**（采纳）vs **静默跳过**。静默会让用户以为守护模式在工作。
- **全屏检查页**（采纳）vs **常驻通知 / Toast**。全屏页要盖住下面不断切换的设置页；`Toast` 会被
  下一次页面切换截断；刚亮屏时通知栏用户未必看得到。全屏页顺带给 `FLAG_KEEP_SCREEN_ON`，
  不必碰 `stay_on`（#731 定过手机版不写插电常亮）。

## Consequences

- 引擎侧新增 `fast.py` 的 `audit` 子命令与模块级审计开关；`off()` 多一条分支。导航点击保留，
  所以审计模式跑偏了照样会点进别的页面——它省的是「改设置」，不是「动手机」。
- 手机版新增 `androidx.work` 依赖、`BOOT_COMPLETED` 接收器（用于「系统更新完成后」比对 build 指纹）、
  一个通知渠道、一个全屏检查页、一个设置项与一份确认清单。
- 四档结局与执行期的**回读**、**未确认**是两套词：回读是「这一次点击生效了没有」，守护复查是
  「现在还是不是目标态」。`CONTEXT.md` 的「守护复查」词条守着这条分界。
- 连续 2 次「找不到」才提示重新适配，沿用的是 `ui_hidden` 的思路：同一处反复出现才当成真信号，
  第一次先当噪音。
- 未真机验证：调度、充电约束在 Doze 与国产 ROM 后台限制下的实际触发率、全屏页的观感都还没有证据。
